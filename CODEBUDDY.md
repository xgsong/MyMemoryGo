# CODEBUDDY.md

This file provides guidance to CodeBuddy Code when working with code in this repository.

## Build & Development Commands

```bash
# Build
make build                    # builds binary to bin/memory
go build -o bin/memory ./cmd/memory

# Test
make test                     # all tests with -race -coverprofile
go test ./...                 # all tests (plain)
go test ./internal/pkg/vector/...   # single package
go test -run TestName ./path/to/pkg # single test

# Benchmarks
go test -bench=BenchmarkCosineSimilarity ./internal/pkg/vector/...
go test -bench=BenchmarkMMRReranker ./internal/infrastructure/search/...

# Lint
make lint                     # golangci-lint run ./...
go vet ./...

# Coverage
make coverage                 # generates coverage/html report

# Run
make dev                      # go run ./cmd/memory/main.go
```

## Architecture

This is a **Go project for AI persistent memory** using clean/DDD layered architecture. Dependencies point inward only.

### Layer Structure

```
cmd/memory/cmd/            -- CLI (Cobra) + HTTP API (Chi) + Composition Root (app.go)
internal/interface/api/     -- REST handlers
internal/application/       -- Use-case orchestration (MemoryApplicationService)
internal/domain/            -- Entities, repository interfaces, domain services
internal/infrastructure/    -- Concrete implementations (SQLite, FileStore, Embedding, Search)
internal/pkg/               -- Shared utilities (vector math, errors, logging)
```

### Key Flow: Store Memory

`CLI/HTTP -> MemoryApplicationService.StoreMemory() -> validate (domain service) -> generate embedding -> persist to SQLite (memories + FTS5 tables + HNSW index)`

### Key Flow: Search Memory

`CLI/HTTP -> MemoryApplicationService.SearchMemories() -> embed query -> HybridEngine.Search() -> concurrent vector (HNSW/brute-force) + fulltext (FTS5 BM25) -> weighted merge -> optional decay -> optional MMR rerank -> filter`

### Core Domain Types (`internal/domain/entity/`)

- **Memory**: Full entry with content, embedding, metadata, checksum, source type, line range
- **Entry**: Lightweight reference (ID, path, snippet, score)
- **SearchHit**: Entry + embedding vector (for MMR)
- **Source types**: `SourceLongTerm` (MEMORY.md, evergreen/never decayed), `SourceDaily` (memory/*.md, temporal decay), `SourceSession` (temporary)

### Repository Interfaces (`internal/domain/repository/`)

Four segregated interfaces: `MemoryRepository` (CRUD), `SearchRepository` (search + index), `EmbeddingRepository` (embed), `FileRepository` (file I/O + watch). `SearchOptions` uses Builder pattern with pointer fields (`*float64`) to distinguish unset from zero.

### SQLite Store (`internal/infrastructure/persistence/sqlite/`)

Single `Store` struct implements both `MemoryRepository` and `SearchRepository`. Schema: `memories` table + `memories_fts` (FTS5) + `embedding_cache`. HNSW vector index loaded in-memory from SQLite at startup. Writes go to both `memories` and `memories_fts` in one transaction, then update HNSW. Schema version tracked in `metadata` table (current: v2).

### Hybrid Search Engine (`internal/infrastructure/search/`)

`HybridEngine` wraps `vectorRepo` + `fulltextRepo` (both point to same `sqlite.Store`). Merges results by weighted score (default vector=0.7, fulltext=0.3), deduplicates by ID. Optional `MMRReranker` (greedy lambda selection) and `TemporalDecayCalculator` (exponential/linear/step strategies; evergreen memories in MEMORY.md are never decayed).

### Embedding (`internal/infrastructure/embedding/`)

Three-layer: `CachedProvider` (LRU, SHA-256 key) -> `OpenAICompatibleProvider` -> HTTP client. Supports OpenAI, Ollama, vLLM, LocalAI via presets (`presets.go`). Embeddings are normalized before storage (making dot product = cosine similarity).

### Composition Root (`cmd/memory/cmd/app.go`)

`InitializeApp()` wires everything: Viper config -> embedding provider (cached) -> SQLite store -> FileStore manager -> HybridEngine (with optional MMR/decay) -> MemoryApplicationService. The same `*sqlite.Store` instance is passed as both `vectorRepo` and `fulltextRepo` to `HybridEngine`.

### CLI Commands

Cobra-based: `init`, `store`, `search`, `sync`, `watch`, `serve`, `version`. Config via `~/.memory/config.yaml` with env var prefix `MEMORY_`.

### REST API (`internal/interface/api/`)

Chi router at `/api/v1/memories` (CRUD) and `/api/v1/search` (POST + GET). ID format contains `/` (e.g., `memory/2026-03-08.md:1-15`), so handlers URL-decode path params.

## Non-Obvious Patterns

- **Memory IDs are deterministic**: `{path}:{startLine}-{endLine}`, generated by `domainService.GenerateID()`
- **Dual embedding in search path**: Both `MemoryApplicationService.SearchMemories()` and `HybridEngine.Search()` generate query embeddings. The service sets `opts.QueryEmbedding` as fallback, but `HybridEngine` uses its own embedder.
- **HNSW delete edge case**: Deleting the last node panics in HNSW, so code rebuilds the graph from scratch when detecting single-node deletion.
- **SearchOptions pointer fields**: `MinScore`, `VectorWeight`, `FulltextWeight`, `MMRLambda` are `*float64` to distinguish "not set" from explicit zero -- always check nil before dereferencing.
- **Embedding normalization is idempotent**: Applied at storage, HNSW build, and query time -- double-normalizing is safe.
